# 런타임 프로파일 — 마부를 Claude Code 밖에서 쓰기

마부의 방법론(Phase 0~7, 생성-검증, 조달·제작의 경계, 트리거 검증)은 런타임과 무관하다.
런타임에 묶이는 것은 **그 방법론을 실행하는 수단**뿐이다. 이 문서는 둘을 분리해,
어떤 에이전트에서든 하네스를 구성할 수 있게 한다.

## 1. 능력 모델 — 제품이 아니라 능력으로 묻는다

Phase 0 환경 감사에서 확인할 것은 "Claude Code인가"가 아니라 아래 네 능력의 유무다.

| 능력 | 있으면 | 없으면 |
|---|---|---|
| **A. 결정론적 오케스트레이션** — 코드가 에이전트 호출 순서·병렬·루프를 강제 | 파이프라인을 스크립트로 박는다 | 오케스트레이터 문서에 순서를 산문으로 쓰고, 각 단계 완료를 사람이 확인 |
| **B. 위임(서브에이전트)** — 별도 컨텍스트의 작업자를 띄움 | 역할별로 나눠 병렬 | 한 세션에서 순차 진행, 단계 사이에 컨텍스트를 파일로 넘김 |
| **C. 에이전트 정의 파일** — 역할을 파일로 두고 재사용 | `.claude/agents/` 같은 정의 디렉터리 사용 | 역할을 **스킬 파일**로 쓰고 위임 프롬프트에서 "이 문서를 읽고 그 역할로" 지시 |
| **D. 스킬 파일** — 지시를 파일로 두고 조건부 로딩 | 도메인 스킬 제작 + 기성 스킬 조달 | 지시를 프로젝트 규약 문서 한 곳에 모음 |

**D는 사실상 어디에나 있다.** `SKILL.md` 형식은 `skills` CLI가 70여 개 에이전트에
설치를 지원하는 공용 배포 형식이다(`npx skills@latest add <owner>/<repo> --agent <id>`).
그래서 **하네스 산출물 중 스킬은 거의 그대로 이식된다.** 갈리는 건 A~C다.

## 2. 프로파일

### claude-code (검증됨)

이 저장소가 실측한 유일한 프로파일이다.

| 능력 | 수단 |
|---|---|
| A | `Workflow` 도구 — `agent()`/`pipeline()`/`parallel()`, schema 검증, `resumeFromRunId` 재개 |
| B | `Agent` 도구 (+ 조건부로 에이전트 팀) |
| C | `.claude/agents/*.md` — frontmatter 전체는 `agent-design-patterns.md` §4 |
| D | `.claude/skills/*/SKILL.md` + `skills:` 사전 로드 |

규약 문서: `CLAUDE.md`.

### generic (능력 탐지형)

Claude Code가 아닌 런타임은 이 프로파일로 시작한다. **제품 이름을 추측하지 말고
사용자에게 묻거나 문서를 확인해 능력 A~D를 채운다.** 확인 안 된 API를 문서에 적는 것이
하네스를 죽이는 가장 흔한 방법이다.

- **A가 없을 때가 기본이라고 가정한다.** 결정론적 오케스트레이션 도구는 아직 드물다.
  이때 마부는 흐름을 스크립트 대신 **오케스트레이터 문서의 번호 매긴 단계 + 각 단계의
  완료 조건**으로 표현하고, 루프 상한·재시도 횟수를 문장으로 못박는다.
  잃는 것은 재현성이며, 그 사실을 산출물에 명시한다
- **C가 없으면 역할을 스킬로 쓴다.** 스킬은 이식되므로, 역할 정의를 `roles/` 스킬로
  두고 위임 프롬프트가 그것을 읽게 하면 A·B가 약한 런타임에서도 재사용이 유지된다
- **규약 문서는 그 런타임이 읽는 파일에 쓴다** — `AGENTS.md`를 읽는 에이전트가 많다.
  어느 파일을 읽는지 모르면 `AGENTS.md`와 런타임 고유 파일 양쪽에 포인터를 두고,
  내용은 한쪽에만 두고 다른 쪽에서 가리킨다(단일 출처)

### 새 프로파일 추가

실제로 그 런타임에서 돌려본 사람만 프로파일을 추가한다. 형식은 위 표와 같고,
**확인한 방법(문서 URL 또는 실행 로그)을 함께 적는다.** 추측으로 채운 칸은 비워 두는
것보다 나쁘다 — 비어 있으면 묻지만, 틀리게 차 있으면 그대로 실행된다.

## 3. Phase 0에서 하는 일

1. 런타임을 식별한다(사용자에게 묻는 게 가장 빠르다)
2. 프로파일이 있으면 로드, 없으면 generic으로 시작해 능력 A~D를 확인한다
3. **확인된 능력만으로 Phase 2 실행 모드를 고른다.** 없는 능력을 전제한 설계는 금지
4. 하네스 CLAUDE.md/AGENTS.md 포인터에 **사용한 프로파일과 확인된 능력**을 적는다 —
   다른 런타임으로 옮길 때 무엇이 깨지는지가 거기서 읽힌다

## 4. 이식성 등급 — 무엇이 따라가고 무엇이 남나

| 산출물 | 이식성 |
|---|---|
| 도메인 스킬 (`SKILL.md`) | **높음** — `skills` CLI 공용 형식 |
| 오케스트레이터의 판단 규칙(브리프 컴파일, 루프 상한, 게이트 기준) | **높음** — 산문이라 그대로 옮겨진다 |
| 에이전트 역할 정의 | **중간** — 내용은 옮겨지나 파일 형식·frontmatter는 런타임마다 다르다 |
| 오케스트레이션 스크립트 | **낮음** — A 능력에 직결. 없는 런타임에서는 문서화된 순서로 강등 |

그러므로 **도메인 지식을 스크립트가 아니라 스킬에 담을수록 하네스가 오래 산다.**
이건 이식성만의 이야기가 아니라, 같은 런타임 안에서도 좋은 설계다.
