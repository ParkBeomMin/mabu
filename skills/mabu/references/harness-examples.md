# 실전 하네스 예시

실제로 구축·운영된 하네스 두 개. 형태가 다른 이유에 주목하라 — 하네스의 모양은
도메인이 아니라 **작업의 제어 흐름**이 정한다.

## 예시 1: 게임 스테이지 공장 (생성-검증 루프)

설득 게임의 스테이지(상황·인물·목표·난이도)를 만드는 하네스. 산출물이 "밸런스"라는
측정 가능한 품질 게이트를 통과해야 한다.

```
.claude/agents/
├── scenario-writer.md    # 시나리오 작가 — 스테이지 JSON 초안
└── balance-tester.md     # 밸런스 테스터 — 초안을 3회 실플레이하고 판정
.claude/skills/
├── stage-craft/          # 작성법: 스키마, 난이도 레버, "breaks가 심장"
├── balance-test/         # 검증법: 무성의/평범/정석 3플레이어 시뮬레이션
└── stage-factory/        # 오케스트레이터 진입점
```

설계 판단들:
- **검증을 "읽고 감상"이 아니라 "돌려보고 숫자"로 정의했다.** 테스터는 세 수준의
  플레이어를 연기해 같은 스테이지를 3회 플레이한다. 합격 기준: 평범한 플레이는 통과선
  미만, 정석 플레이는 이상. 평범이 뚫리면 너무 쉽고 정석이 막히면 불공정 — 둘 다 리젝
- **품질 기준을 판별법으로 썼다.** "breaks(캐릭터가 흔들리는 지점)를 읽고 이기는 대사를
  바로 쓸 수 있으면 합격" — 형용사 기준("구체적으로")보다 판별 가능한 기준이 세다
- **루프 상한 2회.** 2회 수정 후에도 REVISE면 소재 자체의 문제로 보고 사람에게 올린다
- 에이전트 정의에 재호출 지침: "이전 밸런스 리포트가 있으면 지적 항목이 고쳐졌는지부터"

## 예시 2: 세미나 다이제스트 (팬아웃-팬인 파이프라인)

강연 녹음·녹화를 받아 요약 + 카드뉴스 + 인포그래픽 + PPT를 뽑는 하네스.
산출물 4종이 서로 독립이라 팬아웃이 자연스럽다.

```
전사(음성→텍스트, 기계적) → 구조화 요약(판단) → ┬ 카드뉴스
                                              ├ 인포그래픽
                                              └ PPT
```

설계 판단들:
- **모델 배정을 갈랐다.** 전사·포맷 변환은 저비용 모델 + effort low, 요약·구성은 상속
  모델 + effort high. 전 단계 최상위 모델은 청구서만 키운다
- **중간 산출물은 전부 `_workspace/`에 파일로.** 전사가 길어서 반환값으로 나르면
  컨텍스트가 터진다. 파일 경로만 다음 단계에 넘긴다
- **팬아웃 단계는 바리어 없이.** 카드뉴스가 끝나기를 인포그래픽이 기다릴 이유가 없다

## 두 예시에서 일반화되는 것

1. **검증자는 실행자여야 한다.** 읽기 전용 검증(감상평)은 게이트가 아니다. 돌려보고,
   세어보고, 비교한 숫자만 게이트가 된다
2. **루프에는 코드 상한.** "만족할 때까지 반복"을 모델 재량에 두면 비용과 시간이 발산한다
3. **에이전트 수는 제어 흐름이 정한다.** 생성-검증엔 2명이면 족하고, 팬아웃엔 산출물
   종류만큼 필요하다. 머릿수를 먼저 정하고 역할을 끼워 맞추지 마라
4. **환경 제약을 CLAUDE.md에 못박아라.** "이 환경엔 팀 도구 없음 — 서브 에이전트 고정"
   같은 한 줄이 다음 세션의 헛발질을 막는다
