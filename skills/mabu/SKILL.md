# mabu (마부) — 에이전트 하네스 아키텍트

도메인에 맞는 하네스를 구성하고, 에이전트의 역할을 정의하며, 에이전트가 쓸 스킬을 만드는 메타 스킬.

**핵심 원칙 4가지:**
1. **에이전트(누가)와 스킬(어떻게)을 분리한다.** 둘 다 파일로 정의한다 — 파일이어야 다음 세션에서 재사용된다.
2. **오케스트레이션의 기본값은 Workflow다.** 결정론적 제어 흐름(순서·병렬·루프·스키마 검증)은 모델이 아니라 스크립트가 강제한다.
3. **CLAUDE.md에는 포인터만 등록한다.** 트리거 규칙 + 변경 이력. 목록·구조는 파일 시스템이 정본이다.
4. **하네스는 진화하는 시스템이다.** 실행마다 피드백을 받아 에이전트·스킬·워크플로우를 갱신한다.

> 이 스킬은 Claude Code **v2.1.178 이후** 기준으로 작성됐다. 그 이전 버전의
> `TeamCreate`/`TeamDelete` 도구는 제거됐다 — 그 API로 하네스를 설계하지 마라.

## 워크플로우

### Phase 0: 현황 감사

하네스 요청을 받으면 가장 먼저 기존 현황을 확인한다.

1. `프로젝트/.claude/agents/`, `프로젝트/.claude/skills/`, `프로젝트/workflows/`, `프로젝트/CLAUDE.md`를 읽는다
2. **환경 감사** — 설계 전에 이 환경에서 실제로 쓸 수 있는 실행 수단을 확인한다:
   - `Workflow` 도구가 있는가
   - 에이전트 팀이 켜져 있는가 (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` — 켜져 있지 않으면 팀 모드를 설계하지 마라)
   - **설치 스킬 인벤토리**: `~/.claude/skills/`(전역) + 프로젝트 스킬 + 플러그인
     (`installed_plugins.json`) — 조달 가능한 기성 스킬 목록을 만든다
   - 없는 도구·없는 스킬을 전제로 설계하는 것이 하네스 실패의 제1 원인이다
3. 현황에 따라 분기:
   - **신규 구축** → Phase 1부터 전체 실행
   - **기존 확장** → 아래 매트릭스로 필요한 Phase만 실행
   - **운영/유지보수** (감사·수정·동기화) → Phase 7-5로 이동
4. 감사 결과를 요약 보고하고 실행 계획을 확인받는다

**기존 확장 시 Phase 선택 매트릭스:**
| 변경 유형 | P1 | P2 | P3 | P4 | P5 | P6 |
|----------|----|----|----|----|----|----|
| 에이전트 추가 | 건너뜀 | 배치 결정만 | 필수(3-0 포함) | 전용 스킬 필요 시 | 워크플로우 수정 | 필수 |
| 스킬 추가/수정 | 건너뜀 | 건너뜀 | 건너뜀 | 필수(4-0 포함) | 연결 변경 시 | 필수 |
| 아키텍처 변경 | 건너뜀 | 필수 | 영향분만 | 영향분만 | 필수 | 필수 |

### Phase 1: 도메인 분석

1. 사용자 요청에서 도메인/프로젝트 파악
2. 핵심 작업 유형 식별 (생성, 검증, 편집, 분석, 수집 등)
3. Phase 0 결과 기반으로 기존 에이전트/스킬과의 충돌·중복 분석
4. 코드베이스 탐색 — 기술 스택, 데이터 모델, 주요 모듈
5. **사용자 숙련도 감지** — 대화의 용어·질문 수준으로 파악하고 커뮤니케이션 톤을 조절한다

### Phase 2: 아키텍처 설계

#### 2-1. 실행 모드 선택

| 모드 | 언제 | 실행 수단 |
|------|------|----------|
| **Workflow** (기본) | 다단계 파이프라인, 팬아웃, 생성-검증 루프 — 순서·병렬·반복을 코드가 강제해야 할 때 | `Workflow` 도구의 `agent()`/`pipeline()`/`parallel()`/`phase()` |
| **서브 에이전트** | 단발 위임 1~2회, 단계 사이에 사람/메인의 판단이 끼어야 할 때 | `Agent` 도구 직접 호출 |
| **에이전트 팀** (조건부) | 경쟁 가설 디버깅, 발견이 서로의 방향을 바꾸는 탐색·연구·검토. **환경 감사에서 팀이 켜져 있음을 확인한 경우에만** | 자동 팀 형성 + `SendMessage` + 공유 작업 목록 |

**의사결정 순서:**
1. 제어 흐름을 미리 그릴 수 있는가? → 그릴 수 있으면 **Workflow**. 대부분의 하네스가 여기 해당한다
2. 에이전트 호출이 1~2번뿐이고 그 사이에 판단이 필요한가? → **서브 에이전트**
3. 미지 탐색이라 작업 목록 자체가 발견에 따라 바뀌는가? 서로의 이론을 실시간으로 반박해야
   앵커링을 피하는가? → 팀이 적합하다. 이때 팀이 **꺼져 있으면 조용히 강등하지 말고
   사용자에게 알린다**: 이 작업은 팀이 맞다는 근거 + 켜는 법(`settings.json`의 env에
   `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: "1"`, 기존 세션은 재시작 필요) + experimental
   제한 사항을 한 번에 제시하고, 켤지 / Workflow 대체(생성→교차반박→종합)로 갈지
   선택받는다. 팀이 필요 없는 작업에서는 켜라고 권하지 않는다
4. 혼합 가능 — 예: 메인이 서브 에이전트로 정찰 → Workflow로 본작업 팬아웃

**Workflow가 기본인 이유:** 팀·서브 에이전트에서 "누가 다음에 뭘 하나"는 모델의 재량이다.
재량은 실행마다 결과를 바꾼다. Workflow는 순서·병렬·재시도·산출물 스키마를 스크립트가
강제하므로 하네스의 재현성이 코드 수준이 된다. 판단은 각 `agent()` 안에, 흐름은 스크립트에.

#### 2-2. 아키텍처 패턴

파이프라인 / 팬아웃-팬인 / 전문가 풀 / 생성-검증 / 감독자. 각 패턴의 Workflow 구현은
`references/agent-design-patterns.md` 참조.

#### 2-3. 에이전트 분리 기준

전문성·병렬성·컨텍스트·재사용성 4축. 같은 문서의 "에이전트 분리 기준" 참조.

### Phase 3: 에이전트 정의 생성

#### 3-0. 기존 에이전트 중복 검토

신규 생성 전 `프로젝트/.claude/agents/`의 기존 에이전트와 중복을 확인한다. 역할이 겹치는
에이전트가 다른 이름으로 누적되는 것이 하네스 부패의 전형이다.

#### 3-1. 정의 파일

**모든 에이전트는 `프로젝트/.claude/agents/{name}.md` 파일로 정의한다.** Agent 도구의
prompt에 역할을 직접 넣고 끝내는 것은 금지 — 파일이 없으면 다음 세션에서 재사용할 수 없다.

주요 frontmatter 필드 (전체 표는 `references/agent-design-patterns.md`):

```yaml
---
name: balance-tester          # 필수. 소문자-하이픈
description: ...              # 필수. 언제 이 에이전트에 위임하는지
model: inherit                # sonnet|opus|haiku|fable|전체ID|inherit
effort: medium                # low|medium|high|xhigh|max
tools: Read, Bash             # 허용 도구 (생략 시 전체)
skills:                       # 이 에이전트가 뜰 때 사전 로드할 스킬
  - balance-test
isolation: worktree           # 병렬로 파일을 수정하는 에이전트만
memory: project               # 실행 간 지속 메모리가 필요할 때
---
```

**`skills` 필드의 함정:** 팀원(in-process)과 포크에서는 이 필드가 무시된다. 따라서
사전 로드에만 의존하지 말고, **본문에도 "작업 전 {스킬 경로}를 읽어라"를 병기**한다.
이중 안전장치가 아니라, 실행 모드에 따라 하나만 작동하기 때문이다.

#### 3-2. 모델·노력 배정

~~모든 에이전트에 최상위 모델~~ — 이건 낭비다. 작업 성격으로 배정한다:

| 작업 성격 | model | effort |
|----------|-------|--------|
| 설계·검증·심사 등 판단이 품질을 좌우 | `inherit` (또는 상위 지정) | high |
| 수집·변환·포맷팅 등 기계적 반복 | `haiku` | low |
| 애매하면 | `inherit` | 생략(상속) |

`inherit`가 기본값으로 안전한 이유: 사용자가 세션 모델을 올리면 하네스도 같이 좋아진다.
하드코딩하면 하네스가 사용자의 선택을 무시한다.

#### 3-3. 필수 섹션

핵심 역할 / 작업 원칙 / 입력·출력 프로토콜 / 에러 핸들링 / **재호출 지침**(이전 산출물이
있을 때의 행동). 템플릿은 `references/agent-design-patterns.md`, 실전 예시는
`references/harness-examples.md`.

**QA 에이전트 포함 시:** 읽기 전용 타입을 쓰지 마라(검증 스크립트 실행 불가). QA의 핵심은
존재 확인이 아니라 **경계면 교차 비교**이며, 전체 완성 후 1회가 아니라 모듈 완성 직후
점진 실행이다. 상세: `references/qa-agent-guide.md`.

### Phase 4: 스킬 생성

각 에이전트가 쓸 스킬을 `프로젝트/.claude/skills/{name}/SKILL.md`에 만든다.
상세 가이드: `references/skill-writing-guide.md`.

#### 4-0. 조달과 제작의 경계

**기성 스킬은 일반 기술을, 새로 만드는 스킬은 이 도메인의 고유 지식을 담는다.**
둘은 대체재가 아니라 층이 다르다 — 조달했다고 만들 게 없어지지 않는다.

| | 조달 (`skills:`로 물린다) | 제작 (`.claude/skills/`에 쓴다) |
|---|---|---|
| 담는 것 | 어느 도메인에서나 같은 절차 — 디버깅 규율, 코드 최소주의, 검증 게이트 | 이 도메인에서만 참인 것 — 스키마, 난이도 레버, 판별 기준, 실패 유형 |
| 판별 질문 | "다른 프로젝트에서도 그대로 쓰나?" → 예 | "이 프로젝트를 모르는 사람이 쓰면 틀리나?" → 예 |
| 예 | `systematic-debugging`, `hate`, `ponytail` | `stage-craft`(스테이지 스키마·난이도 곡선), `balance-test`(3플레이어 검증법) |

순서:
1. **인벤토리 조회** — 이 작업 유형을 덮는 기성 스킬이 있으면 `skills:`로 물린다.
   매핑·함정: `references/skill-composition.md` **필독**
2. **기존 프로젝트 스킬 중복 검토** — 겹치면 새로 만들지 말고 일반화한다
3. **도메인 스킬 제작** — 하네스마다 최소 하나는 나온다. 안 나왔다면 대개
   도메인 지식을 에이전트 정의 본문에 흘려 넣은 것이다(재사용도 개선도 안 되는 자리)

**에이전트마다 최소 하나의 스킬을 붙인다** — 조달이든 제작이든. 아무것도 안 붙은
에이전트는 "그 역할이 어떻게 일하는지"가 어디에도 없다는 뜻이고, 그건 역할이 아직
정의되지 않았다는 신호다.

**제작 스킬에 넣지 말 것:** 물린 기성 스킬이 이미 말하는 내용. 두 사본은 갈라지고,
갈라지면 어느 쪽이 맞는지 아무도 모른다.

#### 4-1. 구조와 frontmatter

```
skill-name/
├── SKILL.md            # frontmatter(name, description 등) + 본문 <500줄
└── references/ scripts/ assets/   # 조건부 로딩 자원
```

유용한 최신 필드 (전체 표는 `references/skill-writing-guide.md`):
- `context: fork` + `agent:` — 무거운 스킬을 서브에이전트에서 돌려 메인 컨텍스트를 지킨다
- `allowed-tools` / `disallowed-tools` — 스킬 활성 중 도구 제한
- `disable-model-invocation: true` — 사용자 슬래시 전용 스킬 (자동 트리거 방지)
- `when_to_use` — description 보조 트리거 구문

#### 4-2. Description — 적극적 트리거

description은 유일한 트리거 메커니즘이다. Claude는 보수적으로 판단하므로 **pushy하게** 쓴다.

- 나쁨: `"PDF 문서를 처리하는 스킬"`
- 좋음: `"PDF 읽기·추출·병합·분할·OCR 등 모든 PDF 작업. .pdf 파일 언급이나 PDF 산출물
  요청 시 반드시 사용."`

하는 일 + 구체적 트리거 상황 + **후속 작업 키워드**(다시/수정/보완/재실행)까지 포함한다.

#### 4-3. 본문 원칙

| 원칙 | 설명 |
|------|------|
| Why를 설명 | 강압적 지시 대신 이유를 — 이유를 알면 엣지 케이스에서도 올바르게 판단한다 |
| Lean | 본문 500줄 이내. 무게를 벌지 않는 내용은 삭제하거나 references/로 |
| 일반화 | 특정 예시에 오버피팅하지 말고 원리를 쓴다 |
| 반복 코드는 번들링 | 에이전트들이 공통으로 다시 짜는 스크립트는 scripts/에 미리 넣는다 |
| 명령형 | "~한다", "~하라" |

#### 4-4. Progressive Disclosure

Metadata(항상, ~100단어) → SKILL.md(트리거 시, <500줄) → references/(필요할 때만).
500줄에 근접하면 분리하고 "언제 읽으라"는 포인터를 남긴다. 300줄 넘는 reference에는 목차.

### Phase 5: 오케스트레이션

#### 5-1. Workflow 스크립트가 오케스트레이터의 정본이다

흐름 제어를 산문(스킬 본문)으로 쓰면 모델이 매번 다르게 해석한다. **흐름은 JavaScript로
박는다.** 스크립트는 `프로젝트/workflows/{name}.workflow.mjs`로 저장해 버전 관리한다.

```javascript
export const meta = {
  name: 'stage-factory',
  description: '스테이지 생성→검증→등록 파이프라인',
  phases: [{ title: '생성' }, { title: '검증' }, { title: '등록' }],
}
phase('생성')
const draft = await agent(
  `${AGENT_DEF} 읽고 그 역할로 브리프에 따라 초안 작성: ${args.brief}`,
  { label: 'writer', schema: DRAFT_SCHEMA, effort: 'high' })
phase('검증')
const verdict = await agent(
  `초안을 실플레이 3회로 검증: ${JSON.stringify(draft)}`,
  { label: 'tester', schema: VERDICT_SCHEMA })
if (!verdict.pass) { /* 수정 루프 — 최대 2회, 코드로 강제 */ }
return { draft, verdict }
```

핵심 수칙:
- **`schema`로 산출물을 구조화한다.** 파싱 실패·필드 누락을 도구 계층이 걸러 재시도한다
- 에이전트 프롬프트에 `.claude/agents/{name}.md`를 읽으라는 지시를 넣는다 — 정의 파일과
  워크플로우가 어긋나지 않게 하는 접점이다
- 실패는 `null`로 돌아온다 — `.filter(Boolean)` 후 진행하고, 누락은 결과에 명시한다
- 바리어(`parallel`)는 전 단계 결과 전체가 필요할 때만. 기본은 `pipeline`
- 진입은 오케스트레이터 스킬이 맡는다: 트리거 → 컨텍스트 확인 → **브리프 컴파일**
  (거친 요청을 목표·제약·산출물 형식·가정 목록의 구조화 브리프로 번역 — 에이전트 품질은
  브리프 품질을 못 넘는다) → `Workflow({scriptPath, args})` 호출. 스킬이 Workflow 호출을
  지시하는 것은 공식 패턴이다

서브 에이전트 모드의 오케스트레이터와 전체 템플릿: `references/orchestrator-template.md`.

#### 5-2. 데이터 전달

| 전략 | 방식 | 적합 |
|------|------|------|
| **스키마 반환** (기본) | `agent(..., {schema})` → 검증된 객체 | 구조화 산출물, 단계 간 전달 |
| **파일 기반** | `_workspace/{phase}_{agent}_{artifact}.{ext}` | 대용량, 감사 추적, 세션 간 재개 |
| 반환값 | Agent 도구 반환 텍스트 | 서브 에이전트 단발 |
| 메시지 | SendMessage | 팀 모드 한정 |

파일 기반 규칙: 중간 산출물은 `_workspace/`에 보존(감사 추적), 최종 산출물만 지정 경로로.

#### 5-3. 에러 핸들링

1회 재시도 → 재실패 시 해당 결과 없이 진행하되 보고서에 누락 명시. 상충 데이터는 삭제하지
않고 출처 병기. Workflow 디버깅은 transcript 디렉토리의 `journal.jsonl`(각 agent의 실제
반환값 기록)부터 읽는다. 상세: `references/orchestrator-template.md`.

#### 5-4. CLAUDE.md 하네스 포인터 등록

````markdown
## 하네스: {도메인명}

**목표:** {한 줄}
**트리거:** {도메인} 작업 요청 시 `{오케스트레이터 스킬명}` 스킬을 사용하라. 단순 질문은 직접 응답.
**실행 모드:** {Workflow | 서브 에이전트 | 팀} — 환경 감사 결과 명시

**변경 이력:**
| 날짜 | 변경 내용 | 대상 | 사유 |
|------|----------|------|------|
| {날짜} | 초기 구성 | 전체 | - |
````

**넣지 않는 것:** 에이전트/스킬 목록, 디렉토리 구조. 파일 시스템이 정본이고 목록은 썩는다.

#### 5-5. 후속 작업 지원

1. 오케스트레이터 description에 후속 키워드("다시", "재실행", "수정", "~만 다시") 포함
2. 진입 시 컨텍스트 확인: `_workspace/` 존재 + 부분 수정 요청 → 부분 재실행 /
   새 입력 → `_workspace_prev/`로 이동 후 새 실행 / 미존재 → 초기 실행
3. Workflow 중단 재개는 `resumeFromRunId` — 완료된 agent() 호출은 캐시로 즉시 반환된다
4. 에이전트 정의에 재호출 지침(이전 산출물·피드백 반영) 포함

### Phase 6: 검증

상세 방법론: `references/skill-testing-guide.md`.

- **6-1 구조**: 파일 위치, frontmatter(name·description), 참조 무결성, `.claude/commands/`
  미생성 확인
- **6-2 모드별**: Workflow — 스크립트 문법·schema 유효성·바리어 남용 점검, 드라이런 1회
  (스크립트의 agent 프롬프트가 정의 파일을 실제로 가리키는지). 서브 — 입출력 연결.
  팀 — 환경변수 확인부터
- **6-3 실행 테스트**: 현실적 테스트 프롬프트 2~3개. 가능하면 with-skill vs without-skill
  비교. 문제 발견 시 피드백을 **일반화**해 스킬 수정 → 재테스트
- **6-4 트리거 검증**: should-trigger 8~10개 + should-NOT-trigger 8~10개. 핵심은 명백한
  무관 쿼리가 아니라 **경계가 모호한 near-miss**
- **6-5 테스트 시나리오**: 오케스트레이터에 정상 흐름 1개 + 에러 흐름 1개 기술

### Phase 7: 진화

- **7-1** 실행 후 피드백 기회 제공 (강요 금지)
- **7-2** 반영 경로: 품질→스킬 / 역할→에이전트 정의 / 순서→워크플로우 스크립트 /
  트리거 누락→description
- **7-3** 모든 변경을 CLAUDE.md 변경 이력에 기록
- **7-4** 진화 트리거: 같은 피드백 2회 반복, 반복 실패 패턴, 사용자가 하네스를 우회해
  수동 작업하는 것이 관찰될 때
- **7-5** 운영/유지보수: 감사(파일 ↔ 워크플로우 ↔ CLAUDE.md 대조) → 변경은 한 번에
  하나씩 → 이력 갱신 → 검증

## 산출물 체크리스트

- [ ] `.claude/agents/` — 에이전트 정의 파일 (prompt 직접 주입 금지)
- [ ] `.claude/skills/` — SKILL.md(+references), 본문 500줄 이내
- [ ] `workflows/*.workflow.mjs` — Workflow 모드라면 스크립트 파일로 저장
- [ ] 실행 모드 명시 + **환경 감사 근거** (없는 도구 전제 설계 금지)
- [ ] 모델·노력을 작업 성격별 배정 (전부 최상위 모델 금지, 기본 `inherit`)
- [ ] `skills` 사전 로드 + 본문 "읽어라" 병기 (이중 안전장치)
- [ ] 중복 검토 완료 (3-0, 4-0) + 기성 스킬 조달 검토 (skills: 물리기, 미설치 이름 금지)
- [ ] **에이전트마다 스킬이 최소 하나** — 조달이든 제작이든
- [ ] **도메인 스킬이 최소 하나 제작됨** — 없으면 도메인 지식이 에이전트 본문에 갇혔는지 점검
- [ ] 제작 스킬이 물린 기성 스킬의 내용을 중복하지 않음
- [ ] description pushy + 후속 키워드
- [ ] 트리거 검증 (should / should-NOT)
- [ ] CLAUDE.md 포인터 + 변경 이력
- [ ] `.claude/commands/` — 아무것도 생성하지 않음
